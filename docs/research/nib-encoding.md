# NIBArchive encoding of compiled storyboards (Xcode 27.0, ibtool 27.0 / 25098)

Everything here comes from compiling our own storyboards with ibtool and decoding the output. No Apple
binary was disassembled or otherwise analysed. Inputs: the corpus in `Tests/IBCorpus/*.storyboard`
(generated by `scripts/ib-corpus/gen.py`, plus `real-tauri-app`, `xcode-template` and `real-expo-splash-template`), compiled by
`scripts/ib-golden.sh` into `Tests/IBCorpus/golden/<build>/<case>/<flagset>.storyboardc/`. Tools:

- `swift run xless nib dump <file.nib>`: objects and their values.
- `python3 -I scripts/ib-corpus/nib-tables.py <file.nib>`: the raw key table and class-name table with indices,
  which the dump does not show.
- `python3 -I scripts/ib-corpus/check-rules.py [case...]`: the executable form of the rules that are easiest to
  get wrong (object order, objects list, key table, class table, root size, subview geometry, constraint order). It
  checks every golden and fails on any disagreement; it passes on the whole corpus. The constraint arrays of the cases
  the compiler refuses for open questions 1 and 13 (`order-cons-second-item*`, `order-cons-mirrored-*`) and of
  `cons-mixed-horizontal` (attributes rewritten by ibtool) are printed as `OPEN` (exit status 0).
- `python3 -I scripts/ib-corpus/differential.py --seed N [--count 300]` (Mac only, Xcode 27A266a): compiles random
  storyboards with ibtool and with the compiler (`swift run IBDifferential <dir>`, `Sources/IBDifferential`, not a product) and compares the bytes; see section
  6, "Differential check". Not part of `swift test`.

What `check-rules.py` covers: section 3 (object numbering and the objects list), section 4 (key table), section 5 (class table), and
from section 6 the root view size, subview bounds/center and the constraint array order. It does not check the rest
of section 6 (each class's keys, value types and values), nor sections 1, 2, 7 and 8; those are checked by the
compiler's golden tests in Tasks 6–9, which compare whole `.storyboardc` outputs byte for byte with these goldens.

A case name in `backticks` is a corpus case; "u16" etc. are its flag sets (`universal-16` is the default).

> **Booleans.** Value tag 5 means YES and tag 4 means NO. Proof:
> `UIClipsToBounds` is tag 5 when the image view has `clipsSubviews="YES"` and absent without it (`image-no-clips`);
> `UIHidden` appears as tag 5 for `hidden="YES"` (scratch run); `UISystemFont` is tag 5 for system fonts and tag 4
> for Helvetica (`label-system-17-regular`, `label-custom-font`); `UIViewDoesNotTranslateAutoresizingMaskIntoConstraints`
> is tag 5 when the XML says `translatesAutoresizingMaskIntoConstraints="NO"` (`image-with-constraints`).
> `NIBArchiveReader` decodes tag 5 as `.bool(true)` and tag 4 as `.bool(false)`, the writer encodes them the same way, and
> `xless nib dump` and `nib-tables.py` print `true`/`false` accordingly (`NIBBoolTagTests`). This document writes
> **YES/NO**.

## Container

Verified for all goldens (488 at Task 5, 512 after Task 6 added `view-*` and three `device-*` cases; 920 nibs after
milestone 3 Task 6b).

- Magic `NIBArchive`, then `formatVersion` = 1 and `coderVersion` = 10 (UInt32 LE) in every file.
- Header is 50 bytes. The eight UInt32 LE fields are `(count, offset)` pairs in the order objects, keys, values,
  class names. Example, `UIViewController-*.nib` (924 bytes): objects 19 @ 50, keys 19 @ 107, values 43 @ 476,
  classes 7 @ 812.
- Physical section order is objects, keys, values, class names in every golden (so `sectionOrder` is the default).
- Varint (high bit set = last byte), value type tags 0-10, and class-name records (length including trailing NUL,
  extra-int count, Int32 extras, name bytes) parse cleanly. Every object's class index, value range and key index is
  in bounds.

### Trailer after the class-name section

Every golden ends with 4 bytes after the last section: `4C 4E 45 00` (ASCII `LNE` plus NUL). Parsing the class-name
section from its header offset with the header's class-name count consumes exactly up to 4 bytes before EOF in every
file, and the remaining bytes are identical in all files. So the trailer is not part of the class-name table, not a
count mismatch, not an extra entry (`4C` would be a 7-bit length varint with the high bit clear) and not padding
(sections are contiguous).

Handling: `NIBArchive.trailer: Data` holds the bytes after the end of the last section. The reader fills it and the
writer emits it, which gives a byte-identical round trip. `NIBArchive()` defaults the trailer to `LNE\0`. Its meaning
is not known (`IBUINibLNEVersionKey` below suggests "LNE" names ibtool's local nib encoding, but nothing depends on that).

### Layout rule

The reader throws an `.ib` error unless the sections are contiguous in file order (first section at offset 50, each
later one starting where the previous ends), because the writer can only reproduce that layout. Zero-length sections
only need an offset within the file; a zero-length section sharing an offset with a non-empty one is ordered before
it, and co-located empty sections are ordered canonically (objects, keys, values, class names). All goldens satisfy it.

## 1. File set

Every compiled storyboard (`<name>.storyboardc/`) holds exactly three files, for every case and flag set:

| File | Content |
|---|---|
| `Info.plist` | binary plist, section 2 |
| `UIViewController-<vcID>.nib` | the scene's view controller (class swapper), section 6 "View controller nib" |
| `<vcID>-view-<viewID>.nib` | the root view and everything under it |

`<vcID>` is the `viewController` `id`, `<viewID>` the root `view` `id`, verbatim from the XML, any length
(`id-long-ids`: 51-character ids give `UIViewController-VC-a-much-…-0001.nib`). The link step never changes the
files (docs/research/ib-invocation.md).

A view controller with a **`storyboardIdentifier`** (Expo's template: `SplashScreenViewController`) names its nib
`<storyboardIdentifier>.nib` instead of `UIViewController-<vcID>.nib`, verbatim (`vc-storyboard-identifier`,
`-short` "Splash", `-punct` "Launch Screen.v2_x-y+z" with a space; a scratch run with the vcID itself as identifier gave
`01J-lp-oVM.nib`). The view nib keeps `<vcID>-view-<viewID>.nib`. The compiler accepts printable ASCII without "/",
without a leading "." and without leading or trailing spaces, and refuses an identifier equal to the view nib's name
(never compiled with ibtool).

Flag sets do not change the file set. They change content only in one way (section 8): with
`--minimum-deployment-target` ≥ 17.0, a root view without a known device takes its size from the XML frame.

The view-controller nib depends only on the two IDs: all 240 goldens with VC `01J-lp-oVM` and view `Ze5-6b-2t3` have
a byte-identical VC nib. The view nib does not contain any object ID: `id-different-ids` and `real-logo-plus-label`
have identical view nibs, and `order-attrs-shuffled` and `order-constraints-swapped` are identical to it as well
(XML attribute order and XML constraint order do not matter). IDs matter only for the file names and as tie-breakers
in constraint order (section 6, NSLayoutConstraint).

## 2. Info.plist

Binary plist (`bplist00`), the same shape for every case (`xcode-template`, `id-long-ids`):

```
{ UIViewControllerIdentifiersToNibNames = { "UIViewController-<vcID>" = "UIViewController-<vcID>" };
  UIStoryboardDesignatedEntryPointIdentifier = "UIViewController-<vcID>";
  UIStoryboardVersion = 1 (integer) }
```

Byte layout (`xxd`, `xcode-template` u16; 258 bytes):
- Object 0: the top dict, marker `D3`, key refs `01 02 03`, value refs `04 07 08`. Keys in this order:
  `UIViewControllerIdentifiersToNibNames`, `UIStoryboardDesignatedEntryPointIdentifier`, `UIStoryboardVersion`.
- Objects 1-3: the three key strings, ASCII (`5F 10 <len>` then bytes, since every key is ≥ 15 characters).
- Object 4: the inner dict `D1 05 06`; objects 5 and 6: its key and value, **two separate copies** of
  `UIViewController-<vcID>`; object 7: a third copy (the entry point); object 8: `10 01` (integer 1).
  Equal strings are not shared.
- Offset table: one entry per object; entry width 1 byte when every offset is < 256, else 2 bytes
  (`id-long-ids`: 387-byte file, 2-byte offsets). Object references are 1 byte.
- 32-byte trailer: 6 zero bytes, offset-entry size, object-ref size (1), object count (9, 8-byte BE), top object
  (0, 8-byte BE), offset-table offset (8-byte BE).

Strings are ASCII here because IDs are ASCII; a non-ASCII ID was not tested.

With a `storyboardIdentifier` the three strings are the identifier, and the file has **eight** objects, not nine: the
entry point's value is the same object as the inner dictionary's key (object 5), and the inner dictionary's value is a
second copy (object 6); the top dict's value refs are `04 05 07` (`vc-storyboard-identifier-short`, 181 bytes;
every `vc-storyboard-identifier*` and `real-expo-splash-*` golden). `BinaryPlistWriter` expresses this with
`.tagged`/`.ref`.

## 3. Object order

**Objects are numbered in depth-first pre-order of first reference**, starting at the root `NSObject` (#0): an
object gets the next number the first time a value refers to it, and its own values are then walked before the
referring object's next value. Each object's values are contiguous in the values section, in object order (value
ranges start at 0 and follow each other). `check-rules.py` verifies this for every nib.

The graph itself (which object refers to which, in which key order) is fixed per class (section 6). These rules shape it:

1. **Root object** (#0, `NSObject`), keys in this order: `UINibTopLevelObjectsKey`, `UINibObjectsKey`,
   `UINibConnectionsKey`, `UINibVisibleWindowsKey`, `UINibAccessibilityConfigurationsKey`, `UINibTraitStorageListsKey`,
   `UINibKeyValuePairsKey` (the last four point to one shared empty `NSArray`), `IBUINibLNEVersionKey` = int8 1.
   With accessibility elements, `UINibAccessibilityConfigurationsKey` is instead an `NSArray` of
   `UIRuntimeAccessibilityConfiguration`s (section 6); the other three keys still share the empty array, which
   `UINibVisibleWindowsKey` references first (`acc-kinds-order`, `real-expo-splash-template`).
2. **Top-level objects** of the view nib: `[proxy IBFilesOwner, proxy IBFirstResponder, root view]`, so the root view
   is always #6 (#2/#4 proxies, #3/#5 their identifier strings).
3. **Objects list** (`UINibObjectsKey`) of the view nib: `[IBFilesOwner, IBFirstResponder, root view]`, then the root
   view's entry, then the other views' entries **breadth-first**: level by level, in subview order within a level,
   where a view's entry is `[its constraints in array order…, its subviews in order…]` (`order-objects-list`:
   `V, guide, C40 C41 C42 (V's constraints), IMG, LBL, P (V's subviews), C10 C11 (IMG), C17 (LBL), C35 C36 (P),
   N (P's subview), C33 (N)`; `order-objects-bfs` and `order-objects-bfs-constraints`: root → A{A1{A11}, A2},
   B{B1{B11}}, C lists `A, B, C`, then A's, B's and C's entries, then A1's, A2's and B1's, then A11's and B11's — a
   depth-first walk would put A1's entry before B's). Until Task 9's review the corpus had no sibling containers with
   subviews of their own, so depth-first and breadth-first gave the same lists. `check-rules.py` checks this for every
   golden. Special members of the root's entry:
   - safe-area mode: the placeholder `UILayoutGuide` comes right after the root view, before its constraints
     (`real-logo-plus-label`, `core-safearea`);
   - legacy mode: the two `_UILayoutGuide`s come after the root's user constraints and before its subviews
     (`core-legacy-constraints`: `V, C31, C32, guide, guide, IMG`); the generated legacy constraints are not listed.
4. **Value uniquing.** Value objects that are equal are encoded once and shared, across the whole archive:
   strings, colors, fonts (with their descriptors), image placeholders, the empty array (`order-uniquing`: two equal sRGB colors
   from different elements are one `UIColor`; two labels with text "Same" share one `NSString`; the label text "view"
   is the same object as the outlet label "view"; the label text "Logo" is reused as the image's `UIResourceName`;
   two image views with the same image share one `UIImageNibPlaceholder`; `order-cons-items-geometry`: nine views
   share one `"{251, 251}"` hugging string). A system color and an sRGB color with the same components are **not**
   equal (`order-uniquing`: `systemBlueColor` vs sRGB 0/0.533/1 are two objects). Views, constraints and layout
   guides are never shared. Details per value class (Task 8):
   - strings are equal only when their code points are: the NFC and NFD spellings of "Café" are two objects
     (`label-text-forms`), so the compiler compares the UTF-8 bytes, not Swift `String` equality (which is Unicode
     canonical equivalence);
   - equal fonts are one `UIFont` (`label-textstyle-grid`: two Body labels; `label-font-grid`: `type="boldSystem"` and
     `weight="bold"` are the same font), and equal descriptor dictionaries are one object (`label-font-grid`: the eight
     italic fonts share their `{NSCTFontSymbolicTrait: 1}` dictionary);
   - `NSNumber`s are shared by value across `NS.intval` and `NS.dblval`: in `label-font-grid` the italic trait
     `intval 1` (first encoded by the 0.5 pt italic font) is also the `NSFontSizeAttribute` of every 1 pt font, and
     no `dblval 1.0` exists. The first one encoded keeps its form.

## 4. Key interning

The key table is **not** in first-use order. It is the enumeration order of a hash table of key strings:

- **Hash:** CoreFoundation's published 8-bit string hash (`__CFStrHashEightBit` in the open-source CF):
  `h = len; for each 4 bytes b0..b3: h = h*67503105 + b0*16974593 + b1*66049 + b2*257 + b3; for each remaining
  byte: h = h*257 + b; h = h + (h << (len & 31))`, all mod 2^64 (keys are ≤ 96 bytes, so the long-string branch is
  never used). `check-rules.py` has the code.
- **Table:** open addressing with linear probing (`slot = h mod size`, then +1), sizes 3, 7, 13, 23, 41, 71, 127,
  191. Enumeration is slot order.
- **Insertion order:** keys in depth-first pre-order, recorded when a value is encoded and before descending into a
  not-yet-encoded child (the same walk that numbers the objects). Duplicates are not inserted again.
- **Growth:** after inserting a new key, if the count exceeds the size's capacity, the table grows to the next size
  and the old keys are re-inserted in old slot order. Capacities: 13 → 12, 23 → 20, 41 → 33, 71 → 53, 127 → 86.
  These are pinned by the goldens: every one of the 54 distinct key sets of the original corpus (19 to 90 keys)
  matches only with exactly these values. The boundary cases: 34 keys grow to 71 (`color-white-gray`), 28 stay in 41
  (`core-safearea`); 86 keys stay in 127 (`keys-count-86`), 87 and 90 move to 191 (`keys-count-87`, `keys-count-90`).
  The capacities of sizes 3 and 7 cannot be observed: every archive starts with the same first keys
  (`UINibTopLevelObjectsKey`, `NSInlinedValue`, `UINibEncoderEmptyKey`, `UIProxiedObjectIdentifier`, `NS.bytes`, …),
  and any value in 1-2 (size 3) and 3-6 (size 7) gives identical results; `check-rules.py` uses 2 and 6.
  The table of 191 holds at least 107 keys: `keys-count-92` … `keys-count-107` (each step adds one to three keys to
  `keys-count-90`) and `keys-count-legacy` (102 keys, legacy layout guides) follow the rule with no further growth,
  as did all 268 nibs of 91–103 keys in the final review's scratch differential. 107 is also the most keys the
  supported subset can produce: the corpus's goldens use 110 distinct keys in all, three of which
  (`_UILayoutGuideConstraintsToRemove`, `_UILayoutGuideIdentifier`, `UIHidden`) only appear with the legacy guides,
  which exclude the seven safe-area keys. The compiler refuses more than 107 keys (open question 5). Note the
  pattern: each pinned capacity is one more than the capacity CoreFoundation's open-source hash table uses for that
  size (11, 19, 32, 52, 85), which would put the capacity of 191 at 119.
- **Sharing:** a key is stored once per archive and shared by every object and value that uses it
  (`UINibEncoderEmptyKey`, `NS.bytes`, …).

Verified for every nib (`check-rules.py`, rule "key table = hash order"; also `keyTableFollowsCFHashOrderInEveryGoldenNib`).

## 5. Class-name table

- Order: classes in order of first use by an object (object order), then the **fallback** classes that are not
  already in the table, in the order `NSColor`, `NSFont` (`label-plain`: `… UIColor, UILayoutGuide,
  UIRuntimeOutletConnection, NSColor, NSFont`; `cons-two-views-spacing`, where `UIFont` is used before `UIColor`,
  still ends `NSColor, NSFont`).
- `extras`: one Int32, the table index of the class's fallback class. Observed pairs: `UIColor` → `NSColor`,
  `UIFont` → `NSFont`, `_UILayoutGuide` → `UIView`, `_UILayoutSupportConstraint` → `NSLayoutConstraint`
  (`core-minimal`: `_UILayoutGuide extras=[4]` where c4 is `UIView`; `_UILayoutSupportConstraint extras=[8]` where c8
  is `NSLayoutConstraint`, which is also used by objects). No other class has extras. `UIView` and
  `NSLayoutConstraint` are always already present when their dependants are (the root view is a `UIView`; legacy
  guides always come with `NSLayoutConstraint`s), so only `NSColor`/`NSFont` are ever appended. The relative order of
  `NSColor` and `NSFont` was the same in every golden; whether other fallbacks would sort differently is untested.

Verified for every nib.

## 6. Classes

Per class: the keys in the order they are written (a value list is in this order), the value type, the formula or
constant, and the proving cases. `[optional]` keys are omitted under the stated condition. Unless noted, the
listed constant is the same in every golden.

### Common containers

- **`NSArray` / `NSMutableArray`:** `NSInlinedValue` = YES, then one `UINibEncoderEmptyKey` = @element per element.
  `NSMutableArray` is used for `UISubviews`, `UIViewAutolayoutConstraints`, `UIViewLayoutGuides`, the legacy guides'
  `UIViewAutolayoutConstraints`; `NSArray` for the root's lists, the outlet connections, `UILayoutGuideSystemConstraints`
  and `_UILayoutGuideConstraintsToRemove`. The shared empty `NSArray` has only `NSInlinedValue`.
- **`NSDictionary` / `NSMutableDictionary`:** `NSInlinedValue` = YES, then key, value, key, value … each as
  `UINibEncoderEmptyKey`. Entry order observed: ascending key string (all observed dictionaries; see Open questions).
  `NSMutableDictionary` only for the bold system font's descriptor attributes.
- **`NSString`:** `NS.bytes` = data, the UTF-8 bytes, no terminator and no BOM (`label-unicode`: "Olá — 日本語 🚀 \"q\" & <x>"
  is stored as its UTF-8 bytes; XML entities are decoded first). Empty string: data[0]. A 209-byte text has a
  two-byte length varint like any other data (`label-text-forms`). Label text is stored as parsed, with two
  exceptions (section 6, UILabel).
- **`UINibKeyValuePair`:** never emitted. `UINibKeyValuePairsKey` is the shared empty array in every golden; the class
  would carry user-defined runtime attributes, which are outside the supported subset.
- **`NSNumber`:** `NS.dblval` = double (font sizes) or `NS.intval` = integer (font symbolic traits).
- **Integers** use the smallest of int8/int16/int32/int64 that holds the value: 0…127 → int8, 128…32767 → int16
  (`cons-priority-127` int8 127, `cons-priority-128` int16 128), 32768…2^31-1 → int32, negative numbers and values
  ≥ 2^31 → int64 (`cons-relation-le`: `NSRelation` = int64 -1; `UIFontDescriptorOptions` = int64 2147517444). int32
  first appeared with accessibility traits (`acc-traits-grid`: header 65536, header + image 65540, every trait 98303;
  every trait but header is int16 32767); scratch runs with `numberOfLines` 32768, 40000 and 2147483647 gave int32 and
  2147483648 int64 (the compiler still refuses `numberOfLines` above 32767).
- **Points and rects** (`UIBounds`, `UICenter`, `UIShadowOffset`): data = byte `07`, then 2 or 4 little-endian
  doubles. `UIBounds` = `07, 0, 0, width, height`; `UICenter` = `07, x, y`.

### UIProxyObject and outlet connections

- `UIProxyObject`: `UIProxiedObjectIdentifier` = @NSString (`IBFilesOwner`, `IBFirstResponder`,
  `UIStoryboardPlaceholder`).
- `UIRuntimeOutletConnection`: `UILabel` = @NSString, `UISource` = @object, `UIDestination` = @object.
  View nib: one connection, label "view", source IBFilesOwner, destination the root view (every golden).

### View controller nib

Byte-identical for equal IDs (section 1). Objects (`xless nib dump UIViewController-01J-lp-oVM.nib`):
- Root: the 8 keys of section 3.
- Top-level and objects lists: `[proxy IBFilesOwner, proxy IBFirstResponder, proxy UIStoryboardPlaceholder,
  UIClassSwapper]`.
- `UIClassSwapper`: `UIExternalObjectsTableForViewLoading` = @empty `NSDictionary`,
  `UINibName` = "`<vcID>-view-<viewID>`", `UIClassName` = "UIViewController", `UIOriginalClassName` = the same string
  object.
- Connections: `[outlet "storyboard" (source swapper, destination UIStoryboardPlaceholder proxy),
  outlet "sceneViewController" (source IBFilesOwner, destination swapper)]`.
- With a `storyboardIdentifier`: `UIClassSwapper` gets `UIStoryboardIdentifier` = @NSString (the identifier) between
  `UINibName` and `UIClassName`; nothing else changes (`vc-storyboard-identifier*`). The string is shared like any
  other: with the identifier "UIViewController", `UIStoryboardIdentifier`, `UIClassName` and `UIOriginalClassName` are
  one object (`vc-storyboard-identifier-shared`).

### UIView (root view)

Keys: `UIBounds`, `UICenter`, [`UISubviews` = @NSMutableArray, if any subviews or legacy guides],
[`UIBackgroundColor` = @UIColor, if a `backgroundColor`], `UIDeepDrawRect` = YES, [`UIOpaque` = YES, unless
`opaque="NO"`], `UIAutoresizeSubviews` = YES, [`UIAutoresizingMask` = int, unless 0],
[`UIViewAutolayoutConstraints` = @NSMutableArray, if any], [`UIViewLayoutGuides` = @NSMutableArray of the safe-area
guide, if any constraint uses it], [`UIViewInsetsLayoutMarginsFromSafeArea` = int8 0, for
`insetsLayoutMarginsFromSafeArea="NO"`], `UIViewSemanticContentAttribute` = int8 0, `UIViewLargeContentStoredProperties` = nil.

- **Root attributes of Expo's template** (YES/NO only on the root):
  - `userInteractionEnabled="NO"` gives `UIUserInteractionDisabled` = YES in the subviews' position, after `UIOpaque`
    (`root-userinteraction-no`); `"YES"` gives nothing (`root-userinteraction-yes`).
  - `insetsLayoutMarginsFromSafeArea="NO"` gives `UIViewInsetsLayoutMarginsFromSafeArea` = **int8 0** (an integer, not
    a boolean) after `UIViewLayoutGuides` and before `UIViewSemanticContentAttribute`, in safe-area mode with and
    without an owned guide and in legacy mode (`root-insets-no`, `root-insets-no-safearea`, `root-insets-no-legacy`);
    `"YES"` gives nothing (`root-insets-yes`). On subviews it is refused (not compiled with ibtool).
  - `userLabel` changes nothing (`view-userlabel-grid`; also on subviews, below).

- **Size**: `UIBounds` = (0, 0, w, h), `UICenter` = (w/2, h/2), where (w, h) comes from the `<device>`, not the frame
  (`device-retina6_12` with frame 393×852 and the scratch run with frame 375×667 both give 393×852):

  | `<device id>` (portrait) | w × h | case |

  | retina4_0 | 320 × 568 | `device-retina4_0` |
  | retina4_7 | 375 × 667 | `device-retina4_7` |
  | retina5_5 | 414 × 736 | `device-retina5_5` |
  | retina5_9 | 375 × 812 | `device-retina5_9` |
  | retina6_0 | 390 × 844 | `device-retina6_0` |
  | retina6_1, retina6_5 | 414 × 896 | `device-retina6_1`, `device-retina6_5` |

  | retina6_12 | 393 × 852 | `device-retina6_12` (and every modern case) |
  | retina6_3 | 402 × 874 | `device-retina6_3` |
  | retina6_9 | 440 × 956 | `device-retina6_9` |
  | ipad9_7 | 768 × 1024 | `device-ipad9_7` |
  | ipad10_2 | 810 × 1080 | `device-ipad10_2` |
  | ipad10_9rounded | 820 × 1180 | `device-ipad10_9rounded` |
  | ipad11_0rounded | 834 × 1210 | `device-ipad11_0rounded` |
  | ipad12_9rounded | 1024 × 1366 | `device-ipad12_9rounded` |
  | retina3_5 (retired id) | 393 × 852 (the default device) | `device-retina3_5` |

  `orientation="landscape"` swaps w and h (`device-retina6_12-landscape` 852×393,
  `device-ipad12_9rounded-landscape`). `appearance` (light, dark or absent) and an `<adaptation id="fullscreen"/>` child have no effect
  (`device-appearance-dark`, `device-no-appearance`, `device-adaptation-fullscreen` are identical, colors included). With no `<device>` or an unknown
  id: deployment target < 17 → 600 × 600 if `useTraitCollections="YES"`, else 393 × 852; deployment target ≥ 17 →
  the XML frame's width and height (`core-frame-375x667`, `core-frame-1024x1366`, `xcode-template`, `real-tauri-app`,
  `device-unknown`, `core-no-traitcollections`, each u16 vs u17). `check-rules.py` checks this for every golden.
- **`UIAutoresizingMask`**: OR of flexibleMinX 1, widthSizable 2, flexibleMaxX 4, flexibleMinY 8, heightSizable 16,
  flexibleMaxY 32 (`core-autoresizing-<flag>`, `core-autoresizing-all` = 63). No `<autoresizingMask>` element → 36
  (`core-autoresizing-none`); an element with no flags → 0 → key omitted (`core-autoresizing-empty`).
- **Safe-area mode** is on if the document has `useSafeAreas="YES"` *or* the view has
  `<viewLayoutGuide key="safeArea">` (`core-safearea`, `core-safearea-attr-only`, `core-safearea-guide-only` are
  identical). It adds the placeholder `UILayoutGuide` to the objects list. Without either, the nib gets the legacy
  top/bottom guides (`core-minimal`; `<layoutGuides>` elements change nothing: `core-legacy-layoutguides` = `core-minimal`).

### UIView subclasses: UIImageView, UILabel, plain UIView subviews

Common keys, in order: `UIBounds` = (0, 0, w, h) from the XML frame, `UICenter` = (x + w/2, y + h/2) computed in
double from the XML frame (`image-frame-fraction`: x 146.66666666666666, w 99.666666666666671 → center x 196.5;

**Autoshrink** (`label-autoshrink-grid`: 8 factors × 5 sizes and 6 minimum sizes × 5 fonts, every value matches):
- "Fixed Font Size" (`adjustsFontSizeToFit="NO"`): no keys.
- "Minimum Font Scale" (`minimumScaleFactor="f"`, no `adjustsFontSizeToFit`): `UIMinimumScaleFactor` = float(f),
  `UIMinimumFontSize` = pointSize × f **rounded to the nearest quarter point**, halves up (17 × 0.1 → 1.75,
  17.5 × 0.25 = 4.375 → 4.5, 17.5 × 0.75 = 13.125 → 13.25, 12 × 0.01 → 0 → key omitted).
- "Minimum Font Size" (`minimumFontSize="m"`, the React Native template's form): `UIMinimumFontSize` = float(m),

- ibtool warns "Minimum Font Size greater than current font size" when m > pointSize (refused). With a text style
  font the size used is not `NSSize` (Body with factor 0.5 gives 8.5 in a scratch run; refused). Both attributes
  together, `adjustsFontSizeToFit="YES"`, and labels without any of the three attributes (ibtool then writes
  `UIAdjustsFontSizeToFit` = YES and `UIBaselineAdjustment` = 1, scratch run) are refused; Xcode does not write them.

mixed scripts, emoji ZWJ sequences and flags, astral code points, NFC and NFD (two different strings), tabs, newlines
from `&#10;` or a `<string>` with a literal CR LF (the XML parser turns it into LF), leading and trailing spaces,
U+2028, U+2029 and U+0085 all keep their code points. Two changes:
- every **leading U+FEFF** is dropped ("\u{FEFF}BOM" → "BOM", two leading → none, "\u{FEFF}" alone → ""); later ones
  are kept ("mid\u{FEFF}dle", " a \u{FEFF}");
- a **CR from a character reference** (`&#13;`) is inconsistent: "a&#xD;b&#xA;c" and `<string>`
  "One&#13;&#10;Two" become LF, but "&#xD;" and "&#xD;&#xD;" alone keep their CRs (`label-text-carriage-return`). The
  compiler refuses a CR in label text.

Refused because no golden proves them (and Xcode writes them only for features outside the subset): `highlighted`,
`adjustsLetterSpacingToFitWidth`, `preferredMaxLayoutWidth`, a `<color key="highlightedColor">` or `shadowColor`, a
`tintColor`, a missing `<nil key="highlightedColor"/>` (ibtool then encodes `UIHighlightedColor` = blackColor,
scratch run), missing `lineBreakMode` or `baselineAdjustment`, and a named text color without a `<namedColor>`
resource, on which ibtool fails with exit status 255 and no message (as it does for an image view's tint; a missing
named *background* color compiles to the placeholder, `label-color-forms`).

**Plain `<view>` subviews** (`color-system-table`, `order-objects-list`, `view-*`): the common keys (no class-specific ones;

### UIColor

Keys, in order: [`UISystemColorName` = @NSString] or [`UIDynamicCatalogName` = @NSString,
`UIDynamicCatalogUseNibBundle` = YES], `UIColorComponentCount` = int8 (4 RGB, 2 gray), components, `UIAlpha`,
[`UIAlpha-Double`], `NSRGB` or `NSWhite` = data, `NSColorSpace` = int8 (2 RGB, 4 gray).
Components: RGB → `UIRed`, [`UIRed-Double`], `UIGreen`, [`UIGreen-Double`], `UIBlue`, [`UIBlue-Double`];
gray → `UIWhite`, [`UIWhite-Double`]. The plain keys are **float**; a `-Double` key (double) follows a component only
when the color comes straight from decimal input (sRGB, gray gamma 2.2, named-color resource, system table) and the
float differs from the value. Converted colors (P3, calibrated) and the missing-color placeholder never have
`-Double` keys.

The value: for sRGB and gray 2.2 colors written on the element itself (and the system table), each component is first
rounded to **10 significant digits**, as C `%.10g` and parsed back; the float key is that rounded value rounded to
float, and the `-Double` key holds the rounded value and is written only when its float differs from it
(`color-srgb-precision`: 0.123456789012345678 → 0.123456789, 0.33333333333333331 → 0.3333333333;
`color-white-inexact`: 0.3333333333, 0.7; `color-srgb-small-grid`, `color-white-small-grid`, `color-small-forms`:
13/255 → 0.05098039216, 1/255 → 0.003921568627, 1.2345678901234567e-05 → 1.23456789e-05, 1e-11 stays,
0.0999999999949 → 0.09999999999, 0.0123456789050001 → 0.01234567891; 0.3000000268220902 → 0.3000000268, float
0.3 (not 0.30000004, the float of the unrounded input); 0.5000000000001 → 0.5, a float, so no `-Double` key).
Colors equal after rounding are one object (`color-srgb-small-grid`: 0.0123456789050001 and 0.01234567891).
A **named-color resource** is not rounded: its `-Double` keys hold the input values (`color-named-small-grid`:
13/255 → 0.050980392156862744, 0.0123456789050001 stays), and the float is the input's float. Exact floats
(0, 0.25, 0.5, 1, …) get no `-Double` in either form (`color-srgb-alpha`).
A gray whose white or alpha lies within about 1.2e-07 of 0 or 1 (but not on it) is snapped: white 1.1e-07 or 1e-07
with alpha 1 becomes `blackColor` with white 0, 0.99999999 becomes `whiteColor` (`color-white-near-black`,
`color-white-near-white`), while 1e-06, 2e-06, 0.999999 and white 1.1e-07 with alpha 0.5 are kept
(`color-white-small-grid`, scratch runs). The exact tolerance is open question 14; the compiler refuses gray components
closer than 1e-06 to 0 or 1.

`NSRGB` / `NSWhite`: the components formatted like C `%.3g`, separated by one space, followed by the alpha only when
alpha ≠ 1 ("1 0.5 0", "0.25 0.5 0.75 0.5", "0.0001 1e-05 0.123 0.0005", "1.01 0.576 -0.0281", "0.333 0.7", "0 0").

Sources:

- Not resolved (`label-custom-font-missing`, `label-custom-font-grid`): `UIFontDescriptorOptions` = int8 0, the three
  scaling keys **absent**, `UIFontTraits` = 0, whatever the name ("-Bold", "-BoldItalic", spaces, lower case), size
  (12.5 … 100) or `family` (absent or any value).

Which names resolve (scratch runs, Task 8 and its fix round). ibtool resolves an exact, case-sensitive PostScript name
of a font that CoreText reports as available (`CTFontManagerCopyAvailablePostScriptNames()`) on the Mac or in the
iOS simulator runtime, located under `/System`; there is no simpler rule over the sources:
- One scratch compile labelled every such name, 520 in all, plus 5 controls. The names are the 516 Mac names under
  `/System`, which include the 24 PingFang aliases in FontServices' `Reserved/PingFangUI.ttc`, and the 304 runtime
  names, 300 of them shared with the Mac. The resolved form is descriptor options 0x80000000.
  - 301 names resolve: 296 available on both, plus STHeitiSC-Light (Mac only; encoded under the name PingFangSC-Light)
    and the 4 Rockwell faces (runtime only, `Fonts/CoreUI`).
  - 219 do not: 215 Mac-only names (Kokonor, Apple-Chancery, AlBayan, …) and 4 Noto names available on both.
- The PingFang* names are CoreText aliases: the font file's own name table has only dot-prefixed faces
  (`.PingFangUITextSC-Regular`, …), so enumerating font files misses them (the original Task 8 list did).
- Not resolved, besides the 219: lowercase spellings ("helvetica-bold"), full names ("Helvetica Bold"), family names
  ("Avenir Next"), runtime fonts that are not activated (`Fonts/AppFonts` Carlito, BebasNeue, DBLCDTempBlack), and fonts
  the user installed in `/Library/Fonts` or `~/Library/Fonts` (SFCompactDisplay-Black, CascadiaCode-Bold). So the result
  does not depend on what the user installed, only on the Xcode/macOS/runtime fonts. `.SFUI-Regular` maps to Times New
  Roman with a CoreText note on stderr.
- Legacy alias probes (15 names, one compile each): HiraKakuProN-W3, HiraMinProN-W3/-W6, AppleColorEmoji and
  Thonburi-Light resolve, and all are on the list. The off-list probes HeitiSC-Light and GeezaPro-Light do not resolve.
  STXihei makes ibtool hang: it was killed after 60 s, twice. It is refused as **unverifiable** (no ibtool output exists to
  compare with), through the hand-maintained `FontRule.unverifiable` list, which regeneration does not touch.

The compiler encodes every custom font in the "not resolved" form. It refuses (open question 3) any name starting
with ".", and any name that, compared without case, is a PostScript or family name from any of these sources:
- the font files under macOS `/System/Library/Fonts` and the runtime's `System/Library/Fonts` (name tables);
- CoreText's available fonts under `/System` on the Mac (`swift`) and inside a booted iOS 27.0 simulator (an
  iphonesimulator build run with `xcrun simctl spawn`).

The source is `scripts/ib-corpus/available-font-names.swift`. Generating the list
(`scripts/ib-corpus/known-fonts.sh` → `known-fonts.swift` → `KnownFonts.swift`, 1029 names) uses public CoreText calls
and reads names only; two runs give the same file. Against the 525-name compile above, the list has every one of the
301 resolving names. It also has the 219 non-resolving ones: they are refused although ibtool would accept them in
the "not resolved" form, which errs on the safe side. None of the 5 controls is on the list. The custom-font goldens
use names in none of the sources and not installed on the Mac that compiled them (`customFontGoldensUseOnlyUnknownFonts`).

**Residual risk.** The list is a deny-list. A name that ibtool resolves but that is in none of the sources would be
encoded in the "not resolved" form, and the bytes would be wrong. Two kinds of names could do this:
- CoreText legacy aliases that are not "available" names. All the probed ones are covered, but CoreText's alias table
  is not enumerable through public API.
- Fonts that a different Xcode, macOS or runtime version adds.

Keeping it complete:
- regenerate with `known-fonts.sh` whenever Xcode, macOS or the runtime changes (the goldens pin Xcode 27A266a);
- repeat the one-label-per-name scratch compile over the available names, plus controls;
- add any resolving name it finds, together with a refusal test (`refusesCustomFontsThatShipWithMacOSOrIOS`);
- add any name on which ibtool hangs or fails to `FontRule.unverifiable`, with a comment and a refusal test.

### NSLayoutConstraint

Keys, in order: `NSFirstItem` = @item, `NSFirstAttributeV2` = int8, `NSFirstAttribute` = int8 (same value),
[`NSRelation`: ≥ → int8 1, ≤ → int64 -1, omitted for =], [`NSMultiplier` = double, omitted when 1],
[`NSSecondItem`, `NSSecondAttributeV2`, `NSSecondAttribute`], [`NSSymbolicConstant` = @"NSSpace" when
`symbolic="YES"`; the `constant` is then dropped], [`NSConstantV2` = double, omitted when 0], `NSShouldBeArchived` = YES
(user constraints), [`NSPriority` = int, omitted when 1000], [`NSLayoutIdentifier` = @NSString, the `identifier`
attribute of a user constraint, or the identifier of a system constraint], [`NSConstant` = double, same as V2]
(`cons-identifier-placeholder`: `NSPriority` int16 750, `NSLayoutIdentifier` "Lögo top", `NSConstant` 20, in that order).

- Attributes: left 1, right 2, top 3, bottom 4, leading 5, trailing 6, width 7, height 8, centerX 9, centerY 10
  (`cons-*`, `order-cons-table-superview`). Margins (`leadingMargin`, …) and baselines are outside the subset and refused.
  leading/trailing paired with left/right in one constraint is refused: ibtool rewrites the pair (`cons-mixed-horizontal`:
  `A.leading = root.left` becomes `A.leading = root.leading`; in a scratch run `root.right = A.trailing` became a
  trailing constraint) and UIKit rejects such constraints at run time. centerX pairs with both families (`order-cons-table-*`).
- Items are encoded as written: `NSFirstItem` is the `firstItem` even when the sort below swaps the items
  (`real-logo-plus-label`: `safeArea.trailing = label.trailing` keeps the guide first).
- Implicit `firstItem` (absent in XML) is the view that owns the `<constraints>` element (`cons-implicit-firstitem`:
  `<constraint firstAttribute="bottom" secondItem="IMG">` in the root's list → `NSFirstItem` = root view). A view's
  own size constraints have no second item (`cons-width-height`).
- `NSMultiplier` (`cons-multiplier-grid`, 24 spellings; `cons-aspect`, `cons-multiplier-*`):
  - a ratio "a:b" or "a/b" is divided exactly and **rounded to float**, stored as double (16:9 → 1.7777777910232544,
    1/3 → 0.3333333432674408, 21:9 → 2.3333332538604736, 1:1.5 → 0.6666666865348816);
  - a decimal is first **rounded to six significant digits** (C `%g`), then to float: 0.33333333333333331 →
    "0.333333" → 0.33333298563957214 (not float(1/3)), 0.66666666666666663 → 0.6666669845581055, 123.456789 →
    123.45700073242188, 0.0123456789 → 0.012345699593424797, 0.1 → 0.10000000149011612. Scratch runs: 1.0000001
    and 0.9999999 become 1, and 1234567.8 (whose `%g` has an exponent) becomes 1;
  - 1 is omitted: "1", "1.0", "1:1" (`order-cons-own`). The compiler refuses a multiplier that only rounds to 1, a
    decimal outside 0.0001…999999.5 (exponent form in `%g`), non-positive values, ratio components with more than six
    significant digits, and values whose float would depend on the evaluation order (float vs double division, or
    parsing the six digits as float vs double).
- Constants are doubles parsed from the XML string, not rounded (`cons-constant-fraction` 12.333333333333334,
  `cons-constant-negative` -40, `cons-values-grid` 0.5, -0.5, 1000, 0.3333333333333333, -12.25); "0", "0.0" and
  "-0.0" are omitted like an absent constant (`cons-values-grid`).
- `NSPriority`: whole numbers, int8 up to 127 and int16 from 128 (`cons-priority-*`, `cons-values-grid`: 2, 100,
  200, 251, 500, 700, 749, 751, 900, 998); an explicit `priority="1000"` is omitted (`cons-values-grid`).
- `symbolic="YES"` (standard spacing) gives the same `NSSymbolicConstant` for the safe area, siblings and the
  superview (`cons-symbolic`, `cons-symbolic-siblings`); the shared "NSSpace" string is one object.
- Placement: a constraint lives in the array of the view whose `<constraints>` holds it (root list → root view,
  `<imageView><constraints>` → that view, `image-with-constraints`). Its items are that view, the view's direct
  subviews, or (root view) the safe-area guide; Xcode puts a constraint in the nearest common superview of its items.
  Deeper items (open question 7), legacy `viewControllerLayoutGuide`s and unknown IDs are refused.
- Not encoded:
  - **placeholder constraints** (`placeholder="YES"`, removed at build time) are not in the nib, but their items still
    count as constrained for `UIViewDoesNotTranslateAutoresizingMaskIntoConstraints` (`cons-identifier-placeholder`:
    an image view whose only constraint is a placeholder gets the key), and a safe area used only by placeholders
    gets no owned guide and no `UIViewLayoutGuides` (`cons-placeholder-safearea`);
  - **`root.width = item.height` and `root.height = item.width`** with the root view as first item (written or
    implicit) are dropped for every kind of item (image view, label, plain view, safe area) and every relation,
    multiplier, constant and priority (`order-cons-table-superview-flipped`: 30 XML constraints, 28 in the nib;
    `cons-dropped-root-size`). Their items do not count as constrained (an image view in only such a constraint gets
    no `UIViewDoesNotTranslateAutoresizingMaskIntoConstraints`), and a safe area used only by them gets no owned guide
    and no `UIViewLayoutGuides`. A subview owner keeps them (`cons-dropped-root-size`: `P.width = N.height` in P's
    list), and so is `item.width = root.height` (`order-cons-table-superview`) and an aspect constraint
    `IMG.width = IMG.height` in the image view's own list. No other dropped form was seen in 1360 random
    storyboards (below).

**Constraint array order** (`UIViewAutolayoutConstraints`). The XML order and the constraint IDs do not decide it
(`order-constraints-swapped`); it is a sort on these keys, compared in this order, of the encoded constraints.
"Owner" is the view whose array it is; "other" means neither nil nor the owner.

1. Normalise: if `firstItem` is the owner and the second item is another item, swap the two items (attributes stay
   as written).
2. **First item**: the owner itself sorts before everything (`order-cons-owner-first`: a container's own size
   constraints come before those of its subview at (0, 0), with the container's ID "000-aa-aaa", "Mmm-aa-aaa" or
   "zzz-aa-aaa"). Other items by their frame origin (x, y) in the owner's coordinates — the safe-area guide counts as
   (0, 0), subviews use their XML frame — compared by x² + y², then x, then the item's XML ID
   (byte-wise, case-sensitive: "ABD" < "abc") (`order-cons-items-geometry`, `order-objects-list`, `real-logo-plus-label`:
   safe area, then the image at (146.5, 376), then the label at (20, 500)). Widths do not matter here: 70 random
   scratch storyboards with image views, labels and plain views at random frames (widths up to 600, negative
   origins, the safe area as first item) all matched.
3. **Second item kind**: nil or the owner before other items (`order-cons-tiebreaks`; in 900 random scratch
   storyboards no constraint with another second item ever preceded one with the owner as second item).
4. **Attributes** (raw `firstAttribute`, `secondAttribute`), with rank centerX 0, right 1, left 2, trailing 3,
   leading 4, width 5, centerY 6, bottom 7, top 8, height 9:
   - second item nil or the owner: (category, rank(first), rank(second); nil second ranks -1), category 0 if
     centerX is on either side, else 1 if centerY is on either side, else 2 for right/left, 3 for trailing/leading,
     4 for width, 5 for bottom/top, 6 for height, all by the first attribute (`order-cons-table-superview`,
     `order-cons-table-superview-flipped`, `order-cons-own`);
   - other second item: (1 if both attributes are width or both height else 0, rank(first), rank(second))
     (`order-cons-table-sibling` for the safe area, `order-cons-table-sibling-view` for a sibling view).
5. **Priority**, ascending (999 before 1000; `order-cons-tiebreaks`).
6. **Relation**: ≤, then ≥, then = (`order-cons-tiebreaks`).
7. **Second item** (other items only, when they differ): unknown — open question 1. The compiler refuses two
   constraints that reach this step with different second items.
8. **Constraint ID**, byte-wise (`order-cons-tiebreaks`: "ABD-aa-aaa" before "abc-aa-aaa"), but only between
   constraints written in the same direction: when one of two tied constraints was swapped by step 1 (written from the
   owner) and the other was not, ibtool does not order them by ID — open question 13 — and the compiler refuses them.

Constant and multiplier never take part (`order-cons-tiebreaks`). `check-rules.py` implements exactly this (with
the frame x for step 7 and the ID for every tie) and passes for all 102 constraint arrays in the corpus outside the
refused open-question cases.

**Differential check.** `scripts/ib-corpus/differential.py` (seeded, Mac only) generates random storyboards with
`gen.py`'s templates — trees up to three levels deep with one to three subviews per level and sibling containers with
subviews of their own; constraints in every container's list with random attributes of one axis, relations,
priorities, multipliers, constants, symbolic spacing, identifiers and placeholders; own size and aspect constraints;
mirrored pairs; mixed leading/left pairings (which must be refused); 15% without safe area — compiles them with ibtool
and compares the compiler's bytes (`IBDifferential`). Results after the Task 9 review fixes, 1000 storyboards
(seed 1: 226 identical, 74 refused; seed 2: 214, 86; seed 3 with `--count 400`: 281, 119): 721 identical, 279
refused, **0 mismatched**. The refusals: opposite-direction ties (159), mixed pairings (113), second-item ties (4),
placeholders on dropped root cross-size constraints (3). In seed 3, 196 storyboards are three levels deep (122
identical) and 77 have sibling containers with grandchildren (43 identical). Before the fixes the same kind of check
found the breadth-first objects list, the mirrored ties and the mixed pairings (Task 9 review); an earlier scratch run of 360 shallower storyboards had found no mismatch.

## 7. Floating-point encoding

| Key | Type | From |
|---|---|---|
| `UIBounds`, `UICenter`, `UIShadowOffset` | doubles inside data (`07` + LE doubles) | XML frame strings parsed as double; center = x + w/2 in double (`image-frame-fraction`) |
| `NSConstant`, `NSConstantV2` | double | XML string, exact parse (`cons-constant-fraction`) |
| `NSMultiplier` | double holding a float | ratio/decimal evaluated, rounded to float (`cons-multiplier-precise`) |
| `UIRed`, `UIGreen`, `UIBlue`, `UIWhite`, `UIAlpha` of named-color resources | float | value rounded to float |
| `UIRed`, …, `UIAlpha` of element colors | float | the 10-significant-digit value rounded to float (`color-srgb-small-grid`) |
| `UI*-Double` | double | value rounded to 10 significant digits (`%.10g`); named-color resources: the value itself (`color-srgb-small-grid`, `color-named-small-grid`) |
| `NSRGB`, `NSWhite` | text | `%.3g` of each component |
| `UIImageWidth`, `UIImageHeight` | float | constants 1.0 / 0.0 |
| `UIFontPointSize`, `NSSize`, `NS.dblval`, `UIFontPointSizeForScaling`, `UIFontMaximumPointSizeAfterScaling` | double | `pointSize` (or the text-style size for `NSSize`) |
| `UIMinimumScaleFactor` | float | `minimumScaleFactor`, or `minimumFontSize / pointSize` in double (`label-autoshrink-grid`) |
| `UIMinimumFontSize` | float | `minimumFontSize`, or `pointSize × minimumScaleFactor` rounded to a quarter point (`label-autoshrink-grid`) |

XML numbers in Xcode's spelling (zero as `0.0`, integers bare, else 17 significant digits) round-trip exactly
through double parsing; nothing is rounded except where the table says so.

ibtool does not read other spellings the way a general number parser does: in final-review scratch runs
`pointSize="0x11"` gave 12, `red="0x1"` gave 0, and `x="0x10"` and `minimumFontSize="0x8"` differed as well (while
`1.7e1`, `+17` and `5e-1` happened to agree). The compiler therefore accepts only Xcode's spelling
(`XcodeNumber`): an optional minus, digits without leading zeros, an optional fraction; integers (priorities,
`numberOfLines`) without sign or fraction. Exceptions proven by goldens: color components in the exponent form
Xcode writes below 1e-4 (`1.0000000000000001e-05` in `color-srgb-tiny`, `e-06` to `e-12` in `color-srgb-small-grid`)
and a constraint constant of `-0.0` (`cons-values-grid`). A `<color>` with `systemColor` or `name` and components
is refused.

## Open questions

Each item lists the cases that show it. None of them blocks the common launch-screen shapes (`real-centered-logo`,
`real-logo-plus-label`, `real-background-logo-label`, `xcode-template`, `real-tauri-app`, and Expo's
`real-expo-splash-template`, `real-expo-splash-configured`, `real-expo-splash-fullscreen`).

1. **Second-item order (step 7 of the constraint sort).** Only reached when two constraints share the first item,
   both attributes, priority and relation, and point at different other items. `order-cons-second-item` (five 10-wide
   image views) is ordered by the second item's frame x, then the constraint ID, but that rule does not hold in
   general: with the safe area or a label as one of the second items (`order-cons-second-item-safe`: a 393-wide image
   view at x = 10 sorts before the safe area; `order-cons-second-item-mixed`: a label at x = 175.5 before an image view
   at x = 0), and in Task 9 scratch runs even between image views once widths vary (19 of 25 random storyboards with
   image views up to 600 wide missed the x rule; views extending past the root's width tend to sort first). No rule was
   found. The compiler refuses any two constraints that reach step 7 with different second items (all three cases are
   refused tests); `check-rules.py` reports them as known-open.
2. **Color-space conversion** of `displayP3`, `calibratedRGB` and `calibratedWhite` to extended sRGB / gray 2.2.
   The standard published P3→sRGB matrices and transfer function give 1.074044 0.462533 -0.210493 for P3
   (1, 0.5, 0), where ibtool gives 1.0740663 0.4624944 -0.2104380 (`color-p3`); calibrated white 0.5 gives 0.5723068
   (`color-calibrated-white`), not 0.5^(1.8/2.2) = 0.567. The grids `color-p3-grid`, `color-calibrated-rgb-grid` and
   `color-calibrated-white-grid` hold 8, 8 and 6 data points for fitting, but the exact float results were not
   reproduced. Unless they are, these spaces cannot be compiled byte-identically. Task 6 found the shape of the
   calibrated curve: calibrated white w gives the sRGB encoding of w^1.8 (the fitted exponent is 1.8 to 7 digits at
   0.25, 1/3, 0.5 and 0.75), but every float/double evaluation order tried (powf, pow, fused w^0.75, quantised ICC
   parameters) is off by ±1 float ulp on at least one point (0.75 → ibtool `3f4b95bc`, exact formula `3f4b95bb`;
   1/3 → ibtool `3ed0cdb2`, exact `3ed0cdb3`), which suggests table- or approximation-based evaluation. The compiler
   therefore refuses all three spaces.
3. **Custom fonts** that ibtool resolves get their real traits and descriptor options 0x80000000; any other name gets
   options 0, traits 0 and three fewer keys (`label-custom-font`, `label-custom-font-avenir`,
   `label-custom-font-missing`, `label-custom-font-grid`). Resolution was observed only for names CoreText reports as
   available under `/System` on the Mac or in the iOS simulator runtime (section 6); the traits of those fonts are not
   tabulated, so the compiler refuses every such name (a deny-list, with the residual risk stated there). STXihei
   makes ibtool hang, so it is refused as unverifiable (`FontRule.unverifiable`, hand-maintained).
   Which form Xcode produces for an app-bundled font (activated with
   `--auto-activate-custom-fonts` from the app's `UIAppFonts`) was not measured; the compiler produces the
   "not resolved" form (ruling R9).
4. **Device ids** outside the table: `retina3_5` (and `retina6_72` in a scratch run) are sized like the default
   393 × 852; other unknown ids (`unknownDevice`, and `retina5_4`, `ipad10_5`, `ipad11`, `ipad12_9`, `ipad13_0rounded`
   in a scratch run) are treated as no device. The complete list of ids ibtool knows was not enumerated.
5. **Key-table capacity for 191 buckets and up**: no archive in the corpus has more than 107 keys (`keys-count-107`,
   the most the supported subset can produce; section 4), so the capacity of 191 (119 by the CoreFoundation
   pattern) and the next size are unobserved. The compiler refuses archives with more than 107 keys.
6. **Dropped constraints**: placeholders and `root.width = item.height` / `root.height = item.width` are dropped
   (section 6); 1360 random storyboards (differential check) showed no other dropped form, but the forms the compiler refuses (a view
   constrained against itself outside its own list, a placeholder that would also be dropped) were not analysed.
7. **Deeper items in constraint order**: the item origin for a constraint that references a grandchild of the owning
   view (frame converted to the owner's coordinates?) was not tested; `order-objects-list` only has a child-level
   constraint inside a nested view. The compiler refuses items that are not the owner, its direct subviews or its
   safe-area guide.
8. **Dictionary entry order**: every observed `NSDictionary` (font descriptors, at most four entries) is in ascending
   key order; it could also be hash order.
9. *(Resolved in milestone 3 Task 6b.)* **int32 width**: 32768…2^31-1 encode as int32 (`acc-traits-grid`, scratch
   `numberOfLines` runs; section 6, "Common containers").
10. **SF Symbol names**: ibtool gives the symbol form only to names it knows and the asset form to any other name
    (section 6, UIImageNibPlaceholder). Its list of names was not enumerated (it would have to come from the Xcode
    installation), so the compiler accepts only the 38 names of `image-symbol-grid` and refuses other
    `catalog="system"` names.
11. *(Resolved in Task 9.)* A view that only owns constraints between other items (its subviews) and is no item of
    any constraint does not get `UIViewDoesNotTranslateAutoresizingMaskIntoConstraints`, with or without
    `fixedFrame="YES"` (`cons-owner-not-item`).
12. **Carriage returns in label text** from character references (`&#13;`) become LF in some texts and stay CR in
    others (`label-text-carriage-return`); the compiler refuses them. Literal CRs never reach the compiler: XML
    parsing turns CR LF and CR into LF.
13. **Ties between constraints written in opposite directions** (step 8 of the constraint sort). `X.top = owner.bottom`
    and `owner.top = X.bottom` tie through step 6 once step 1 swaps the second, but ibtool does not order them by ID
    (`order-cons-mirrored-tie`; 10 of 32 scratch variants in the Task 9 review). With the same attribute on both sides
    the root view's goldens follow the IDs (`order-cons-mirrored-same`), but a subview owner's do not
    (`order-cons-mirrored-nested`, and 5 cases in a run of the differential check). No rule was found; the compiler
    refuses every tie between a constraint written from the owner and one that is not.
14. **Gray colors near black or white.** ibtool snaps a gray-2.2 component that is within a small tolerance of 0 or 1
    to exactly 0 or 1 and then uses the named color (`color-white-near-black`: white 1.1e-07 → `blackColor`;
    `color-white-near-white`: 0.99999999 → `whiteColor`). Scratch runs put the tolerance near float epsilon (1.1e-07
    snapped; 1.2e-07 and 1.1920928955078125e-07 kept), but whether it applies with other alphas and to the alpha
    itself was not pinned down. The compiler refuses gray white or alpha values closer than 1e-06 to 0 or 1 (other
    than 0 and 1); `color-white-small-grid` proves 1e-06 and 0.999999 are kept.
15. **Accessibility beyond the traits** (milestone 3 Task 6b): only the traits element was compiled with ibtool.
    `label`, `hint`, `identifier`, `isElement` and other children or attributes of `<accessibility>`, an
    `<accessibility>` without traits, and trait names outside the 16 of `acc-traits-grid` (ibtool silently ignored
    `tabBar` and `frequentAdds`) are refused.
16. **Expo-only spellings elsewhere** (milestone 3 Task 6b): `true`/`false` are proven only for `clipsSubviews`,
    `userInteractionEnabled` and `translatesAutoresizingMaskIntoConstraints` on subviews, and
    `insetsLayoutMarginsFromSafeArea` only on the root view; the same spellings or attribute elsewhere are refused.
    `storyboardIdentifier`s outside printable ASCII, with a leading "." or surrounding spaces, or equal to the view
    nib's name were not compiled with ibtool and are refused.
